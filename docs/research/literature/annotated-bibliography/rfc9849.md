IETF. 2026. "TLS Encrypted Client Hello (ECH)." *RFC 9849*. https://www.rfc-editor.org/info/rfc9849

## Research Problem

TLS 1.3 encrypts most of the handshake, but the ClientHello message still exposes sensitive metadata—particularly the Server Name Indication (SNI)—to on-path observers. The problem is to design a mechanism that encrypts the remaining cleartext metadata in the ClientHello while preserving TLS's existing security properties.

## Objective

To specify the Encrypted Client Hello (ECH) extension for TLS 1.3 (and DTLS 1.3) that encrypts the ClientHello to the TLS server, protecting SNI, ALPN, and other sensitive fields from passive network observers.

## Methodology

- Defined ECH extension with two ClientHello messages:
  - ClientHello Outer (CHO): contains dummy information, visible to on-path observers.
  - ClientHello Inner (CHI): contains real connection information, encrypted using HPKE (Hybrid Public Key Encryption).
- Specified ECH key configuration and distribution via DNS SVCB/HTTPS records.
- Defined downgrade resistance, anonymity set requirements, and security considerations.
- Analyzed threat model for passive and active attackers.

## Features

- Encrypted ClientHello extension type.
- ECH config identifier.
- Outer and inner ClientHello structures.
- HPKE public key encapsulation.
- SNI, ALPN, and other ClientHello fields moved to encrypted inner payload.

## Results

- ECH encrypts SNI and ALPN in TLS 1.3, closing the last major cleartext metadata leak in the handshake.
- Connections to servers in the same anonymity set become indistinguishable from one another.
- ECH provides downgrade resistance: connections that attempt ECH cannot be downgraded to cleartext by attackers.
- ECH is not sufficient alone to protect server identity (DNS, IP address, and other channels may still leak).
- Active attackers who control DNS can strip ECH configurations or supply fake ones.

## Limitations

- Does not protect against active attackers who can modify DNS responses or inject fake ECH configurations.
- ECH adoption depends on DNS-based configuration distribution; DNSSEC and encrypted DNS are recommended but not required.
- Server operators must carefully deploy ECH to maximize anonymity set size.
- May interfere with legitimate network security controls (URL filtering, selective decryption, compliance monitoring).
- Creates operational challenges for SOCs that rely on SNI for threat detection and policy enforcement.

## Relevance to ETTH

**Very High.** ECH directly threatens the visibility assumptions underlying ETTH's proposed methodology. If ECH adoption becomes widespread, SNI-based features and many TLS fingerprinting techniques will lose their effectiveness. ETTH must design its scoring system to remain useful even when SNI is encrypted, potentially relying more heavily on JA4 Outer ClientHello fields, flow-level behavioral metadata, and server certificate analysis.

## Evidence We Can Use

1. **Visibility loss:** ECH encrypts SNI and ALPN, removing the most widely used network-visible indicator for destination identification.
2. **Fallback behavior:** If ECH configuration is unavailable, clients must not fall back to unencrypted ClientHello (prevents downgrade attacks).
3. **Outer ClientHello remains:** Some TLS handshake features remain visible in the Outer ClientHello, potentially including cipher suites, extensions, and JA4-relevant fields.
4. **DNS dependency:** ECH configuration is distributed via DNS, making DNS visibility critical for ECH-aware monitoring.

## Questions Raised

1. Which JA4 fingerprinting fields remain visible in the Outer ClientHello under ECH deployment?
2. Can ETTH's flow-level behavioral features compensate for SNI loss in ECH environments?
3. What operational strategies (e.g., endpoint-based TLS inspection, selective decryption) can maintain visibility without violating privacy?
4. How prevalent is ECH in real-world traffic, and how quickly is adoption growing?
